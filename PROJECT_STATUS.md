# PROJECT STATUS — Nykaa Fashion redesign (prototype)

_Source of truth: [`docs/PRD.md`](docs/PRD.md). Last updated: 31 Oct 2026._

**This branch — `claude/nykaa-fashion-awards` (direction v4):** the same product, structure and behaviour as `claude/nykaa-fashion-grid-redesign` (kept untouched as the current design), re-finished in the register of an awards-recognised fashion site, at the owner's request ("more modern like an awards website — copy the interaction, the motion, the theme, update a few layouts, bigger imagery on the homepage in a few sections"). **Theme:** warm studio-paper surfaces taken from the photographs' own walls (`bone` / `paper` / `sand`), warm-black ink and buttons, raspberry kept for accents; display type at poster scale (up to 9 rem, weight 500, −0.058 em); wider section rhythm. **Motion:** Lenis smooth scroll, word-mask headline reveals, rise / fade / picture reveals from one IntersectionObserver, parallax frames, ticker, a follower cursor with Drag / View labels, drag-to-scroll rails, page fades via `template.tsx`; only transform / opacity / clip-path animate, so the no-shadow / no-gradient / no-blur rules still hold. **Safety:** nothing is hidden unless JS runs and motion is allowed (`html.js` is withdrawn after 5 s if hydration fails; reduced motion shows everything; touch screens keep native scroll and get no cursor). **Layouts:** the home page gets full-bleed picture bands, a ticker and statement, hover-driven category and brand lists, a full-height Diwali feature, drag rails and a large shop-the-look; other pages get finish, not new flows. Art direction, primitives and the rules QA enforces: [`docs/AWARDS_DIRECTION.md`](docs/AWARDS_DIRECTION.md). Not checked against awwwards.com itself — the site was unreachable from the build environment, so the patterns are the conventions those entries share.

**Direction (v3, current):** an *improved Nykaa Fashion*, not a different brand. After the first grid pass was rejected as "not Nykaa Fashion", 15 live screenshots and the official wordmark were supplied and became the source of truth for look and copy: white surfaces, slate text, **navy primary buttons**, **raspberry accent**, **green savings**, blue "Responsible" labels, the supplied logo, the live header (Women · Men · Kids · Home · More ▾ + department row + Fashion | Luxe + Account / Wishlist / Cart), footer, login modal, bag drawer, wishlist and product-page structure. On top of that identity the structure is rebuilt: one 12-column grid (4 on phones), a different composition per section, flat colour, **no shadows** (the live site uses them; an explicit requirement here), **one typeface (Inter Display)**, working top + bottom navigation. Grid and layout contract: [`docs/GRID_SYSTEM.md`](docs/GRID_SYSTEM.md). The PRD's curation assets (Hidden Gems, Luxe, Responsible, Style Files, House of Nykaa) stay in view as sections and under **More ▾**. Everything backend-shaped is **simulated and labelled**.

**Content status:** structure, wording, category names, footer labels and brand names come from the supplied screenshots and the PRD audit; products, prices, discount stamps, ratings and imagery are **sample data** (stamps are computed from the catalogue so a banner never promises more than its listing). The domain `www.nykaafashion.com` was allowed in the environment's network policy, but the site's CDN (Akamai) answers `403 Access Denied` to this environment — even to a stock browser — so the live catalogue **could not be imported**. To use real data, supply an export (HAR / JSON / CSV, or saved pages) from a normal browser and replace `src/data/home-content.ts`, `labels.ts`, `catalog-defs.ts`; Global Store, Revolve, Fitzone, Lingerie and Activewear are not built.

## What is simulated (always labelled in the UI)

Personalisation / intent engine (localStorage heuristics) · OTP sign-in (code is `123456`) · payments and saved payments (test values shown; `fail@upi` and card `…0002` decline on purpose; only a UPI ID or a card’s brand and last four digits are stored) · orders, tracking & returns · reviews · delivery estimates · coupons (`TASTE10`, `FIRSTEDIT`, `GEMS15`, `HOUSE200`) · back-in-stock alerts · analytics events (logged locally, PRD §8.1) · **New & Next:** the sample launch brands, dates, prices and codes (`VRISA20` …), *Notify me* (saved in the browser, nothing sent), pre-launch wishlist, and the prototype launch clock (a cookie that moves the site's time so a reviewer can watch a launch happen).

The **Prototype** panel (footer → “Prototype controls”, or the menu drawer on phones) lets a reviewer force intent states, add latency, fail the next request, hide a home module (partial failure), read the event log, sign in as the demo account, and reset everything.

## Decisions

- **Stack:** PRD §9.1 — Next.js + TypeScript + Tailwind + Framer Motion + Lucide. Repo was empty, so scaffolded with the current `create-next-app` (Next 16.4, Cache Components, Turbopack). No other runtime deps.
- **Cache Components rules respected:** no `Date.now()`/`Math.random()` during render (`useNow`, seeded PRNG), `useSearchParams` behind `<Suspense>`, `await params` behind `<Suspense>` with skeletons, header wrapped for `usePathname`.
- **State:** a ~60-line external store (`src/lib/store.ts`) on `useSyncExternalStore` with localStorage/sessionStorage persistence — hydration-safe, no state library.
- **Data model:** PRD §6.5 in `src/data/*`. Plain erasable TypeScript so Node scripts import it directly.
- **Brands:** House of Nykaa labels are used as named in the PRD; every other label/product is fictional (no implied real catalogue or prices).
- **Typography:** one family — Inter at optical size 32 (`font-variation-settings: "opsz" 32` = Inter Display), self-hosted (`public/fonts`, OFL) so the build never calls a font CDN, no other face anywhere; headings weight 700 with raspberry emphasis; small text keeps the same optical size (a deliberate trade-off: slightly tighter than the text cut, offset with +0.004em tracking). ₹ comes from Inter's latin-ext subset. **Flat rules:** no `box-shadow`/`ring`/`drop-shadow`/gradient/backdrop-blur/blend/grain; focus is a 2px outline; overlays are a 1px line over a flat scrim; corners are 4px on controls (a layered base rule), pills for size/filter chips and toggles, 16px on dialogs, square on images and cards, circles by nature (avatars, swatches, pins, radios, count badges). Enforced by `scripts/qa/flat.cjs`. **Palette:** page `#fff`, surfaces `#f7f8f8`/`#f0f4f4`, ink `#1c2834`, navy `#001425` (primary buttons), raspberry `#982854` (links, active underlines, badges; AA 7.6:1 on white), green `#357a41` (savings), blue `#2b62d4` (labels), maroon `#6c1038` (login band), wordmark magenta `#FC2779` (logo artwork only).
- **Image loading policy:** every `<Img>` takes a `load` hint — `preload` for the single LCP image visible at every breakpoint, `eager` for the first grid row, `high` for desktop-only images (lazy, so a hidden copy never downloads, but first in the queue when shown); default is lazy. The home hero is one art-directed `<picture>` (tall cover on phones, wide on desktop) so a phone never fetches or preloads the other. Rails and below-the-fold grids never preload.
- **Touch targets (PRD §7.4):** standalone controls are 44px; small text links get an invisible 44px hit area on coarse pointers (`tap` utility); small buttons grow to 44px on touch (`Button size="sm"`, quick add, helpful). Footer links get 44px pitch on touch.
- **Hosting:** `src/proxy.ts` (Next 16 proxy) is a password gate for any host — `SITE_PASSWORD` → signed HttpOnly cookie via its own sign-in page, fail-closed on Vercel when unset, noindex everywhere, pictures served directly behind the cookie on Vercel; README → "Host it on Vercel". Verified locally with the gate on, in self-hosted and Vercel (`VERCEL=1`) modes (wrong password, forged / expired / extended cookies, open-redirect attempt, protected pictures and optimiser, locked and opt-out). **Deployed 31 Oct 2026 (awards branch):** Vercel project `nykaa-fashion-awards` (personal Hobby scope), production URL set by the owner (kept out of the repo while it is public), deployed with the Vercel CLI after the owner approved a device login; `SITE_PASSWORD` is a generated sensitive variable for Production and Preview. Not connected to GitHub (the Vercel GitHub app has no access to the repo), so pushes do not redeploy — run `vercel deploy --prod` again, or connect the repo. Verified live in a real browser: sign-in page, wrong and right password, cookie flags (Secure, HttpOnly), pages and pictures with the cookie, 401 for pictures without it, robots.txt public, motion classes active. The live check caught a real bug — with pictures served directly (`images.unoptimized`) `getImageProps` returns no `srcSet`, so the hero lost its 16:9 art direction on desktop; fixed, and `home.cjs` now asserts which hero picture is shown.
- **Imagery:** only the two supplied photographs are used, everywhere (an explicit instruction after the procedural product art was rejected). `scripts/placeholders/fill.mjs` cuts all 571 images from them at each key’s own size: the product name picks the window (kurta set for Indian wear and kids, the suit for western, shoes, earrings, the bouclé chair for soft furnishings, the vases for decor), front / alt / detail views and colour variants are different windows or mirrors, and scenes get full-figure, wide and close crops with shoppable pins on the garment in frame. Portrait windows that reach past the photograph extend the seamless studio backdrop — the figure is never altered, nothing is recoloured. Consequence: every product looks like one of two photographs; real product photography replaces files of the same name. The earlier procedural art engine was removed (it remains in git history).
- **Imagery from the owner's AI-generated set (1 Nov 2026, staging only):** the owner generated the first 60 pictures from docs/IMAGE_PROMPTS.md and put them, named by shot id, in a Figma file (`Mj8oos8GHlgEeY4fKgrJpY`, page *Images*). They were fetched through the Figma connector (`download_assets` → `rawImages`, the uploaded files), kept as originals in `scripts/figma/source/`, and cut into 91 site pictures (4 home banners + their ratio sets, 5 category tiles, 9 edits × wide / tall, 6 stories × 4, 6 New & Next brands × hero / galleries, 3 pop-ups, plus the pop-up video re-cut from `vrisa-wide`) by `scripts/figma/build.mjs` — the existing picture builder of `scripts/unsplash` pointed at a second library, with a small patch (a manifest may re-map the home banners and pop-ups, and mark a close-up photo to be used whole). Shoppable pins sit on the garment they name, with the catalogue product that matches it. The home hero's festive slide and the Diwali band got their own pictures (new banner subjects `festive-set`, `diwali-band`; the band is dark, so its copy is white from 1024 px). The New & Next banner's date and countdown moved from the top right to the left column at 1280 px+, because the campaign pictures put the subject right of centre. `/credits` lists every picture as AI-generated; the footer-level claim of the old rule ("only the two photographs") now applies to product pictures only. Known flaws, all in docs/IMAGE_SET.md: the sources are small (1376 × 768 / 928 × 1152 / 1264 × 848 / 1200 × 896), so tall cuts of wide pictures are a little soft; `story-diwali-1` has a blank band and is cropped (regenerate); `home-hero-coord` was cropped 64 px at the left (a dark window frame sat behind the headline).

- **Home order and deal intent:** the sale banner is the first module in every intent mode and **Shop by category is always the second fold** (owner request, 31 Oct 2026). Deal intent (set by any offer interaction — copying a coupon, sorting by discount, opening Offers or the Offer Edit, a sale link — and kept for the browser session) promotes the dark offer band to the slot right under the category tiles (it once sat above the banner, which read as "the banner is missing"); a returning visitor's "picked for you" rail takes third place. `journey.cjs` asserts `hero, categories, offers` for a sale-link arrival and `categories.cjs` that the tiles are the second module.
- **Shop by category (second fold):** a picture-tile grid (six across from 1280 px, four from 1024, three from 600, two on phones; phones show five categories and the last tile) after the Myntra reference the owner shared — layout only: flat colour, Inter Display, the 12-column grid, no gradient frames. Each tile is a real category: department, name, "Up to X% off" (the deepest discount in it, computed from the catalogue) and "Shop now"; the last tile and the "View all 23 categories" button open a dialog (a bottom sheet on phones) listing every category by department with style counts, focus-trapped and closed with Escape. Replaces the earlier "What are you looking for?" index. Tile pictures are the category's top-ranked product picture, so they get better as product pictures do. **It starts right under the banner:** the ticker and the one-paragraph statement ("House labels and big names … gathered by occasion") used to be part of the banner module and pushed the tiles about 1,350 px down — three screens, which the owner could not find ("can't see the shop by category"); they are their own module, `intro`, placed right after the tiles, and `categories.cjs` asserts there is no gap between the banner and the section and that it starts within a screen and a quarter.
- **Headline masks:** poster-scale headings split into words inside overflow-hidden masks; the display type is tracked up to −0.058em, so the last letter of a word (the "s" and "&" in "Tops & Tees") reached past its mask and was cropped on every listing title. The mask now has 0.1em of room either side (negative margins keep the layout), and `scripts/qa/clip.cjs` renders every revealed heading on 33 routes × 5 widths with and without the masks and fails on any difference (it runs with motion allowed — under reduced motion the masks do not exist).
- **Sign-in notification (not a database):** the admin asked to know only whether the people the prototype was shared with have actually opened it — "someone signed in" and when, for user accounts only, with no other data, no stored records and no tracking. A server-side login store (Redis, with device and country) was built first, tested, and **reverted before it ever shipped** because it collected and kept more than was asked. What ships: when a *user* account authenticates, the proxy POSTs one plain line to `LOGIN_NOTIFY_URL` (ntfy.sh, Discord, Slack, or any plain-text endpoint) — "Someone signed in to the prototype — Sat, 31 Oct 2026, 4:42 pm IST" — with a 1.5 s timeout and errors swallowed, so a dead endpoint never blocks a sign-in. No Login ID, device, browser, IP or location is sent; admin sign-ins, wrong passwords and refreshes send nothing; nothing is stored on the site. The dashboard's browser-only records stay as they were and now point at the notification.
- **Add user (admin dashboard):** the gate is server-side, so a browser-only list could not let anyone in; with no database the server therefore *issues* a sign-in — a Login ID plus a generated password `XXXX-XXXX-XXXX-XXXX` whose first group is the expiry (hours since 1 Jan 2026) and the rest a 60-bit HMAC over (Login ID, expiry) — and recomputes it at sign-in. Works on any device, cannot be extended or moved to another ID, nothing stored. Issued accounts are always regular users, sessions use their own token shape (`i.…`) that expires with the access, `/api/admin/*` is admin-only in the proxy *and* in each handler (same-origin check too). Limits stated in the UI and README: no instant revoke (`SITE_REVOKED` + redeploy, or change `GATE_SECRET`), the list of added users is per browser, no chosen passwords. A KV / Postgres store is the upgrade if those matter.
- **Pop-ups (PiP):** one `PromoPip` mounted in the root layout draws whatever `pickPromo()` (pure, unit-tested) selects; campaigns are data (`promos.ts`) and a `launchId` campaign derives its words from `launches.ts` and follows the prototype launch clock. Built to not interrupt: appears after `delaySeconds` on browsing pages only (never bag / checkout / login / account / admin / prototype, even when forced; product / help / info only if listed), waits while any overlay is open, never takes focus, one at a time, dismissal keeps a campaign away 7 days and everything else for 24 h, a visit shows at most two (urgent campaigns, priority ≥ 100, are the one exception), an opened campaign stays away 14 days. Video: muted, looping, inline, paused when the tab is hidden or a dialog covers it, not autoplayed under reduced motion or data saver, Pause / Play chip, mute chip only when `hasAudio`. Layout: phones get a docked mini window (square thumbnail + words, ~80 px) above the bottom bar using the same `--bottom-nav-h` / `--sticky-h` offsets as the toasts; ≥ 600 px a 4:3 window (200 px, 264 px from 1024) in the bottom-right corner. Memory (dismissed / opened) is localStorage like the other stores; the sample clip is a Ken-Burns of the supplied photograph (`scripts/placeholders/promo-video.mjs`, 640×480, 8.5 s, ~290 KB mp4 + ~310 KB webm). QA scripts import `scripts/qa/quiet.cjs` so a pop-up never interferes with checks about something else.
- **New & Next (launch template):** a brand is one object in `src/data/launches.ts` plus pictures — name / wordmark, campaign pictures, launch and early-access times, headline and description, offers, product previews, CTA — and every surface (hub, brand page, rows, preview sheet, ticker, product page brand line) is driven by it; `npm run data:check` validates it. **Plugged in as lookup only:** launch brands and pieces are added to `labelById`, `productById`, `productBySlug` (and `launchProducts`) but never to `labels` / `products`, so listings, search, recommendations, the brands directory and the home page are byte-for-byte what they were; a piece still gets a product page, quick view, wishlist heart and a bag line once it is on sale. **One rule drives the state:** `isLaunched(launch, now)`. Pages are statically generated and the server renders at a fixed prototype time (30 Oct 2026) so hydration agrees; the browser then evaluates the real clock (or the prototype launch clock cookie `nf_launch_offset`) and flips the page when the moment passes, without reload. **Pre-launch guards:** `src/proxy.ts` redirects `/p/<launch piece>` to its launch page until launch time (the launch clock cookie is honoured), and `addToBag` refuses with "Not on sale yet" whatever path led there. **Graduation:** after launch, move a brand's pieces into `catalog-defs.ts` and its label into `labels.ts` so it joins search and listings (steps in `docs/LAUNCHES.md`).
- **Unsplash photography (31 Oct 2026) — tried and stopped:** the owner asked for Unsplash pictures "matched to the Indian audience" (the live site's own pictures were ruled out: nykaafashion.com refuses this environment and they are copyrighted). A full pipeline was built and tested without a key (`scripts/unsplash`: 44 search groups, cached searches with numbered contact sheets, picking with focus points and product-labelled pin anchors, downloads reported to Unsplash, a build that cut 144 site pictures from 52 photographs with colour-aware product windows, wide banners with the subject right of the copy and an exposure fit for heading contrast, credits on `/credits`, `data:check` rules, two unit tests), phase A (home banners, categories, edits, stories, New & Next, pop-ups) was picked by eye, built, passed the full QA and went live on request. After seeing it the owner judged the pictures not relevant and asked to stop using Unsplash and to stop fetching images (a public clothing-image dataset they pointed to was cloned moments earlier and never opened). **State now:** every picture, the pop-up clip, the picture metadata, alt texts and footer restored from `cd9ca82`; the supplied-photograph rule below applies again; the toolkit and `/credits` stay in the repo, dormant (`docs/UNSPLASH_PLAN.md`); the Unsplash key was deleted from the environment and should be revoked by the owner (it was shared in a screenshot).

- **Release workflow — staging first (owner's standing instruction, 31 Oct 2026):** everything new is built on `claude/nykaa-fashion-staging` and published to a separate review site (`nykaafashion-neelesh-staging.vercel.app`, a Preview deployment of the same Vercel project, behind the same sign-in); production (`claude/nykaa-fashion-awards`, `nykaafashion-neelesh-design.vercel.app`) changes only when the owner says a build is final, through `PROMOTE=yes scripts/release/deploy.sh production`, which also refuses any commit that is not on the live branch. A staging build is marked by a yellow strip above the header and "(staging)" in the tab title, driven by `NEXT_PUBLIC_RELEASE_CHANNEL` (`src/lib/channel.ts`); production builds carry none of it. Staging sends no sign-in notifications (`LOGIN_NOTIFY_URL` is Production-only). Procedure, promotion and rollback: `docs/RELEASE.md`; the rule for future sessions is in `CLAUDE.md`.

- **Full-bleed home layout (31 Oct 2026, staging only):** at the owner's request, a second home layout in which pictures run edge to edge with no gutter and no page margin and tiles touch (docs/BLEED_LAYOUT.md). Same page grid (4 / 12 columns) at a zero gap, with a row unit of 1.25 column units so a tile spanning *c* columns and *c* rows is exactly 4:5; a wall is built from blocks of twelve base cells (a feature is four), which makes a complete rectangle at every width (2 / 3 / 4 / 6 across) — measured by `scripts/qa/bleed.cjs`. Words sit on solid white strips or the tile is flat colour (no gradient scrims); the heart is never inside the link. Switch: staging bar, *Prototype controls → Home layout*, or `?layout=bleed|classic`; the build's default is bleed on staging and classic on production (`DEFAULT_LAYOUT`, `src/lib/layout.ts`). The classic page is untouched. With two source photographs every wall repeats the same people in different crops — the layout needs real photography to land; flat colour tiles (price, brands, Diwali, computed edits) carry the rhythm until then.
- **Keep exploring — retention / rabbit-hole MVP (31 Oct 2026, staging only):** an endless feed as the last module of the home page and the last section of every product page, in both layouts (docs/RABBIT_HOLE.md): every piece carries its reason ("Because you browse Dresses", "Completes the look", "Under ₹1,999"), a product page's feed is seeded by the product and each piece opens another product page with its own feed, it loads itself three times then waits for a tap so the footer stays reachable, its order is fixed while you look, and "Pick up where you left off" (full-bleed, returning visitors) rises to third. Simulated and labelled (heuristic scoring over local signals, seeded jitter, nothing leaves the browser). A scroll-memory layer for "Back returns to the same tile" was built and **removed**: tested 14 product pages deep and six routes away, Next 16 with Cache Components already keeps visited pages alive (React `Activity`), so the feed length and scroll position survive; `scripts/qa/rabbit.cjs` guards it. Listing and search pages do not end in the feed yet (phase 2).
- **Launch video (1 Nov 2026, staging only):** at the owner's request, a 97.6 s launch film for the new look (docs/LAUNCH_VIDEO.md). It is made from the site itself rather than generated: Playwright captures the production build state by state (33 stills at 2×, plus the rectangles of tiles / chips / buttons), a small HTML timeline engine draws each scene as a pure function of time, headless Chrome renders the frames and ffmpeg encodes them (`scripts/video/`, one entry point `build.sh`). The score is synthesised (numpy; nothing sampled, nothing to license). Captions instead of a voice-over — no voice service was available; the doc carries a one-line-per-scene script and a silent cut for it. The Higgsfield video-montage / video-editing workflows were reviewed and not used (cloud editors; the footage is a private, access-gated prototype; the account has no credits). Every claim on screen maps to a script that ran (the proof scene lists them and says in its fine print that these are automated checks, not an accessibility audit), "sample data" is stated in the first and last scenes, and the adaptive-home scene is labelled simulated. Colour: Chrome's JPEG frames are BT.601 full range, converted to BT.709 limited range and tagged, verified on flat swatches (within 2 of 255 levels). The finished MP4s are build output, not committed.
- **New imagery — AI-generated, first 60 pictures (1 Nov 2026):** the owner will replace the two supplied photographs with pictures made on an image-generation site, starting with the 60 that carry the key pages (4 home banners, 5 category tiles, 9 edits, 18 story pictures, 21 New & Next brand pictures, 3 pop-ups; the other ~130 product pictures come after). docs/IMAGE_PROMPTS.md and docs/image-prompts.csv hold one prompt per picture, each named by the file name it must be sent back under, with its aspect ratio (16:9 ×25, 4:5 ×20, 3:2 ×12, 4:3 ×3) and the composition the layouts need (wide banners: the person right of centre, the left 45% plain for the headline, a 4:5 crop around them must also work). The prompts carry no brand names or logos; the Kids tile is garments only (no children's faces). Until the pictures arrive the two supplied photographs remain the only imagery. When they arrive: cut every slot from them (scripts/placeholders / scripts/unsplash build tooling can be reused), set focus points and pin anchors, review contact sheets, add an \"AI-generated\" line to the credits page, staging first.
